# Plan

This plan builds Hookd 1/6, Signed event delivery, as described in `requirements.md` and `design.md` in this folder. Requirement IDs (R1–R18, N1–N5) refer to `requirements.md`. Every task ends with `go build ./...` and `go test ./...` passing with no outside service.

## S1: Foundation

Set up the Go module, configuration, and the small standalone packages that have no database: IDs, secrets and signing.

### T1.1: Module skeleton, configuration and logging

Depends on: none

Create the Go module, the layout from the design (`cmd/hookd`, `internal/config`, and so on), and `internal/config`. It reads every `HOOKD_*` variable from the design's Configuration table, with the listed defaults, and fails with a clear message on bad values (for example a non-duration `HOOKD_POLL_INTERVAL` or an unknown `HOOKD_DB_DRIVER`). Set up `log/slog` with `HOOKD_LOG_LEVEL` and `HOOKD_LOG_FORMAT`. `cmd/hookd` dispatches the subcommands `serve`, `migrate` and `account create`, which are stubs for now and print "not implemented".

Done when: `go run ./cmd/hookd` prints usage, each subcommand runs, and unit tests cover every setting's default, an override from the environment, and the rejection of invalid values.

### T1.2: IDs, signing secrets and API keys

Depends on: T1.1

Build `internal/ids`:
- prefixed ULID generation (`acct_`, `ep_`, `msg_`, plus a prefix for deliveries and keys),
- endpoint secret generation (`whsec_` + base64 of 24 random bytes from `crypto/rand`),
- API key generation (`hk_` + 32 random bytes in base64url), with a function returning its SHA-256 hash and display prefix.

Done when: unit tests check formats and prefixes, that IDs sort by creation time, that secrets decode to 24 bytes, and that two calls never return the same value.

### T1.3: Standard Webhooks signer

Depends on: T1.2

Build `internal/signing`. Given a secret, message ID, timestamp and body, it returns the `webhook-id`, `webhook-timestamp` and `webhook-signature` headers (`v1,<base64 HMAC-SHA256>` over `id.timestamp.body`, with the key being the decoded secret after `whsec_`) (R14). Add the official `standard-webhooks` Go library as a test dependency.

Done when: tests sign several bodies, including empty, unicode and large ones, and the official library verifies each one. A known test vector from the Standard Webhooks spec gives the expected signature, and a tampered body or a wrong secret fails verification.

## S2: Store

The `Store` interface and its SQL implementation for SQLite and PostgreSQL. The `deliveries` table doubles as the work queue.

### T2.1: Store core, migrations, accounts and API keys

Depends on: T1.1, T1.2

Build `internal/store`:
- the `Store` interface,
- the SQL implementation with a dialect layer (placeholders, types, claim query) and a constructor that opens SQLite or PostgreSQL from config,
- embedded migrations for each dialect, creating all five tables and indexes from the design's data model,
- a migration runner that records which migrations it has applied.

Implement account creation, API key creation (only the hash is stored), and looking up an account by key hash. Wire up `hookd migrate`, and `hookd account create --name <name>`, which prints the account ID and the plain API key once. Make `HOOKD_AUTO_MIGRATE` apply migrations on start-up. Add a test helper that gives each test a fresh migrated SQLite database in `t.TempDir()`.

Done when: running `migrate` twice is a no-op the second time, `account create` prints a key whose hash is found by the lookup, and store tests pass on SQLite.

### T2.2: Endpoint storage

Depends on: T2.1

Add endpoint methods to the Store, all scoped by account ID:
- create, with a secret generated by T1.2 and `event_types` stored as a JSON array,
- get, without the secret,
- get secret,
- list with `limit` and an `after` cursor,
- update `url`, `description`, `event_types` and `enabled`,
- soft delete.

Deleted endpoints are never returned or updated.

Done when: tests cover every method, pagination, and cross-account access (another account's endpoint behaves as not found, in reads and in writes). They also check that a deleted endpoint disappears from lists and gets.

### T2.3: Event storage, fan-out and idempotency

Depends on: T2.2

Add `CreateEvent`. In one transaction it:
1. handles the idempotency key: it returns the existing event if one with the key exists within `HOOKD_IDEMPOTENCY_WINDOW`, and clears the key on an older match,
2. inserts the event,
3. selects the account's enabled, non-deleted endpoints, keeps those whose `event_types` is empty or contains the type, and inserts one `pending` delivery for each (R10, R11, N2).

It reports whether the event was new. Add `GetEvent`, which returns the event with each delivery's endpoint ID, status, response status and error (R12), scoped by account.

Done when: tests show that fan-out goes only to matching, enabled endpoints, and that an event with no matching endpoint has no deliveries. Repeating a key within the window returns the same event and creates no new deliveries. Repeating it after the window, using an injectable clock, creates a new event. Events of other accounts are not visible.

### T2.4: Delivery claim, lease and result

Depends on: T2.3

Add:
- `ClaimDelivery`: atomically takes one row that is `pending`, or `in_progress` with an expired `locked_until`, and sets it to `in_progress` with `locked_until = now + lease`. PostgreSQL uses `FOR UPDATE SKIP LOCKED`; SQLite uses a single `UPDATE … RETURNING`.
- `RecordDeliveryResult`: sets `succeeded` or `failed`, the response status, error, latency and `attempted_at`.
- a lookup that loads the event and endpoint for a claimed delivery, including whether the endpoint is disabled or deleted.

Done when: tests show that a claimed row is not claimed again while its lease is valid, that it can be reclaimed after the lease expires (injectable clock), that concurrent claimers on SQLite never get the same row, and that results are stored and shown by `GetEvent`.

### T2.5: Run the store suite on PostgreSQL

Depends on: T2.4

Make the Store tests run against PostgreSQL when `HOOKD_TEST_PG=1` is set, using the `HOOKD_DB_*` settings. Each run creates a unique schema, migrates it and drops it at the end. Without the variable these tests are skipped. Add a concurrent-claim test that runs only on PostgreSQL, with several goroutines and connections, to confirm `SKIP LOCKED` never hands out a row twice.

Done when: `go test ./...` passes without PostgreSQL (the PostgreSQL tests are skipped), and with `HOOKD_TEST_PG=1` against a local PostgreSQL the whole store suite passes on both dialects.

## S3: HTTP API

The developer-facing API from the design, using only `net/http`.

### T3.1: Server, errors, auth and health

Depends on: T2.1

Build `internal/api`:
- the server on `HOOKD_LISTEN_ADDR`,
- the JSON error helper (`{"error":{"code","message"}}`) (N5),
- the bearer-auth middleware, which hashes the key, looks it up, puts the account in the context, and returns 401 when the key is missing or invalid (R2),
- `GET /healthz`, which checks the database,
- graceful shutdown on SIGINT/SIGTERM.

Make sure `Authorization` headers and keys are never logged (N4). Wire `hookd serve` to start the server.

Done when: `go run ./cmd/hookd serve` answers `/healthz` with 200. `httptest` tests cover 401 for a missing, malformed and unknown key, success with a valid key, and that the request log contains no key material.

### T3.2: Endpoint routes

Depends on: T3.1, T2.2

Implement `POST/GET /v1/endpoints`, `GET/PATCH/DELETE /v1/endpoints/{id}` and `GET /v1/endpoints/{id}/secret` (R4–R8):
- `url` must be absolute, `http` or `https`, with a host,
- event types must match `[A-Za-z0-9._-]{1,128}`,
- create returns the secret,
- other accounts' IDs give 404.

Done when: `httptest` tests cover every route, the validation errors with their codes, pagination, enable/disable, delete, and isolation between accounts.

### T3.3: Event routes

Depends on: T3.1, T2.3

Implement:
- `POST /v1/events`: checks the event type, that the payload is valid JSON, and that it is no larger than `HOOKD_MAX_PAYLOAD_BYTES` (413 when it is). It reads the `Idempotency-Key` header and returns 202 for a new event or 200 for an idempotent repeat (R9, R10). After a new event is committed, it sends a non-blocking signal on a wake channel that the API is given.
- `GET /v1/events/{id}`: returns the event and the delivery status for each endpoint (R12).

Done when: `httptest` tests cover a valid send, an invalid type, invalid JSON, an oversized payload, idempotent repeats, the wake signal firing once per new event, lookup with pending deliveries, and 404 for other accounts.

## S4: Delivery

The workers that sign and send events, the verifying test receiver, and the end-to-end acceptance test.

### T4.1: Sender and worker pool

Depends on: T1.3, T2.4, T3.3

Build `internal/delivery`:
- an HTTP sender: `POST` with `Content-Type: application/json`, the signed headers from T1.3 and a `User-Agent: Hookd/1` header, a `HOOKD_DELIVERY_TIMEOUT` timeout, redirects not followed, and the response body read up to 64 KB and thrown away,
- a pool of `HOOKD_WORKERS` goroutines. Each claims a delivery and fails it with `endpoint_disabled` if the endpoint is disabled or deleted. Otherwise it signs and sends the delivery once and records the outcome: `succeeded` on 2xx; `failed` on anything else, with the status or error text (R13–R18). Workers wake on the API's signal or every `HOOKD_POLL_INTERVAL`, and stop cleanly on shutdown.

Wire the pool into `hookd serve`.

Done when: tests with `httptest` receivers show:
- a 2xx answer is marked succeeded,
- 500 and 302 answers are marked failed with their status,
- a hanging receiver fails on timeout (shortened by configuration in the test),
- a refused connection fails with an error,
- a disabled endpoint is not called,
- the received headers verify with the official library,
- a delivery left `in_progress` with an expired lease is sent after the pool restarts (N2).

### T4.2: Verifying test receiver

Depends on: T1.1

Build `cmd/testreceiver`, which is not deployed. It is an HTTP server with flags `--addr`, `--secret` and `--status`. It checks each request with the official Standard Webhooks Go library, logs the event ID, type, body and whether it verified, and answers with the configured status (default 200).

Done when: a test run of the receiver accepts a request signed by T1.3 with status 200 and logs "verified". A tampered request is logged as not verified, and `--status 500` makes it answer 500.

### T4.3: End-to-end acceptance test

Depends on: T3.2, T4.1

Write one Go test that runs the whole service in-process on a fresh SQLite database and follows the seven acceptance steps from `requirements.md`:
1. create an account and key through the store/CLI code path,
2. register an `order.paid` endpoint and a `user.created` endpoint on `httptest` receivers,
3. send `order.paid` and check that only the first receiver is called,
4. check that the received request verifies with the official library and the endpoint's secret,
5. check that `GET /v1/events/{id}` shows the delivery succeeded,
6. check that a 500 receiver shows as failed with status 500,
7. check that a second account's key gets 404 for the first account's endpoints and events.

Done when: the test passes with `go test ./...`, finishes in a few seconds, and fails if any of the seven checks is broken (for example, if signing is turned off the test fails).

## S5: Documentation

### T5.1: Setup, deployment and testing documentation

Depends on: T1.1, T1.2, T1.3, T2.1, T2.2, T2.3, T2.4, T2.5, T3.1, T3.2, T3.3, T4.1, T4.2, T4.3

Write `README.md`, with detail under `docs/` where it helps. It covers:
- **Set up and run from scratch**: install Go, clone the repo, `go run ./cmd/hookd serve`, create an account, then register an endpoint pointing at `cmd/testreceiver` and send an event with `curl`, ending with the receiver logging "verified".
- **Configuration**: the full table of every `HOOKD_*` setting, what it does and its default.
- **Deploy to production**: build the binary, prepare the PostgreSQL node (create the database and user, grant rights, set `sslmode`), set the `HOOKD_DB_*` settings, run `hookd migrate`, run one or more instances behind a load balancer, check health with `/healthz`, and create accounts.
- **Test locally**: `go test ./...`, and how to run the PostgreSQL suite with `HOOKD_TEST_PG=1`.
- **API reference**: a short summary of the API with `curl` examples, and a receiver verification example using a Standard Webhooks library.

Also fill in the "Build & Test" and "Architecture Overview" sections of `CLAUDE.md`.

Done when: someone who has never seen the project can follow each of the three guides (local setup, production deploy, local testing) from start to finish on a new machine, and every command in them works as written.
